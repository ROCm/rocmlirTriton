patch193499.patch
----------------------------------------------------------------------
- Upstream PR     : https://github.com/llvm/llvm-project/pull/193499
- Upstream commit : 81d618b6bc1e71cda79fe7bf9cbab63933dd5975
- Upstream title  : [AMDGPU][SIInsertWaitcnts] Fix iota_range assertion
                    when OtherMarks is empty in mergeAsyncMarks()
- File Fixed      : llvm/lib/Target/AMDGPU/SIInsertWaitcnts.cpp

Symptom without the patch
-------------------------
rocmlir-driver -c aborts during code generation with:

  Assertion `Begin <= End && "Begin must be less or equal to End."' failed.
  Stack frame: WaitcntBrackets::mergeAsyncMarks ->
               seq_inclusive<unsigned>(1, 0) -> iota_range ctor

The bug fires at a CFG join where one predecessor has pending async
memory operations (ASYNCMARK / WAIT_ASYNCMARK pushed onto AsyncMarks)
and the other does not. MergeCount becomes min(0, N) = 0 and the loop
`for (auto Idx : seq_inclusive<unsigned>(1, MergeCount))` violates
Begin <= End. The fix adds an early `return StrictDom` when
MergeCount == 0.

Regression test that guards this patch
--------------------------------------
mlir/test/fusion/nightly-misc-e2e/attention-i8-SIInsertWantcnts.mlir

  Compile-only. Cross-compiles attention -t i8  and pipes through 
  `rocmlir-driver -c`. FileCheck pattern `CHECK: triton.hsaco` requires 
  successful codegen; reverting this patch makes rocmlir-driver abort and 
  FileCheck's stdin is empty.

patch198508.patch
----------------------------------------------------------------------
- Upstream PR     : https://github.com/llvm/llvm-project/pull/198508
- Upstream commit : ace44dc5a2a48e5d024bc5c015f69a67cd9be909
- Upstream title  : [AMDGPU] Gate `S_LSHL[1-4]_ADD_U32` patterns on uniform
                    results
- File Fixed      : llvm/lib/Target/AMDGPU/SOPInstructions.td
- Contents        : SOPInstructions.td fix plus the 13
                    llvm/test/CodeGen/AMDGPU/*.ll LIT test updates
                    (CHECK-line-only; no logic). All hunks verified to apply
                    cleanly against the pinned LLVM (87717bf9).

Symptom without the patch
-------------------------
On gfx1201 (RDNA4, wave32), grouped convolution with split-K > 1 (packed
f16 atomics) produces incorrect output: ~6 of every 8 consecutive output
channels are zeroed. The miscompile only appears at LLVM middle-end
opt level >= 2 (rocmlir-driver --gO>=2, i.e. the default); --gO=1 was the
prior workaround.

Root cause
----------
The s_lshlN_add_u32 selection patterns added by upstream PR#167032
("Generate s_lshl?_add_u32", commit 125b6b591741, present in the pinned
LLVM) are not gated on uniformity. At -O2, GVN + InstCombine reassociate
the per-lane output-channel offset into a `(workitem.id-derived << 2) +
base` shape that matches the scalar S_LSHL2_ADD_U32 pattern even though
the value is divergent (IR UniformityAnalysis correctly marks the whole
chain divergent). SIFixSGPRCopies then satisfies the SALU operand by
inserting `v_readfirstlane_b32` on the divergent channel, collapsing every
lane to lane 0's channel index -> the per-lane packed-f16 atomic stores
all target the same channel, dropping the rest.

The companion SDAG divergence-tracking fix (PR#147560, commit
9293b65a616b) that would have caught this was reverted in the pinned LLVM
by PR#152548 (commit c7c022948031), so the missing UniformBinFrag gate is
the actionable fix.

The fix wraps each pattern in `UniformBinFrag<shlN_add>` (matching the
other SOP2 scalar patterns in the file) so divergent shl/add chains select
the vector `V_LSHL_ADD_U32` instead. Drop this patch on the next Triton
bump that pulls commit ace44dc5a2a4 into the pinned LLVM (it lands after
the current pin 87717bf9, dated 2026-04-08; the fix merged 2026-05-19).

mlir-rocm-runtime-standalone.patch
----------------------------------------------------------------------
- Upstream PR     : https://github.com/llvm/llvm-project/pull/205651
- Upstream title  : [MLIR][ROCm] Build mlir_rocm_runtime STANDALONE
- File Fixed      : mlir/lib/ExecutionEngine/CMakeLists.txt
                    mlir/lib/ExecutionEngine/RocmRuntimeWrappers.cpp
- Contents        : Marks mlir_rocm_runtime STANDALONE so it no longer links
                    LLVMSupport, mirroring mlir_cuda_runtime, and replaces
                    the remaining SmallVector/ArrayRef use in
                    mgpuMemHostRegisterMemRef with plain C++ pointer/stride
                    logic.

Symptom without the patch
-------------------------
Loading libmlir_rocm_runtime.so in a process that also reaches ROCm's
libLLVM.so aborts during dynamic initialization with:

  SmallPtrSet.h:301: Assertion `Bucket < End' failed.

This fires whenever the runtime is dlopen-ed (mlir-runner --shared-libs, or
the Python lit harness) in an environment whose ROCm comes from the
_rocm_sdk_devel (TheRock) pip package: libmlir_rocm_runtime.so's DT_NEEDED
chain libamdhip64 -> libamd_comgr -> libLLVM.so loads a second LLVM, and
comgr's bundled libLLVM happens to share the exact 23.0git soname.

Root cause
----------
libmlir_rocm_runtime.so was not built STANDALONE, so add_mlir_library linked
LLVMSupport into it, exporting default-visibility llvm::* symbols
(llvm::cl::SubCommand, ManagedStatic, CommandLine, ...). With both LLVMs in
the process the dynamic linker interposes these data symbols, so the two
instances share LLVM's cl::opt / pass-registry singletons and one tears the
other's SmallPtrSet apart during static init.

Why STANDALONE
--------------
RocmRuntimeWrappers.cpp's only LLVM use was SmallVector/ArrayRef in
mgpuMemHostRegisterMemRef. Replacing it with plain pointer/stride logic lets
the library drop LLVMSupport entirely (STANDALONE), so there are no LLVM
symbols left to clash. This matches the intent of upstream commit 351ae0ca550c
("[MLIR][CMake] Fix runtime libraries with PCH"), which made the other
dlopen-ed runtimes STANDALONE but left mlir_rocm_runtime on a
DISABLE_PCH_REUSE workaround because it still used LLVM ADTs. See
ROCm/TheRock#4981.

Drop this patch on the next LLVM/Triton bump that pulls the upstream PR into
the pinned LLVM.

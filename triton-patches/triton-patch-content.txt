patch-gfx1310-isa-family.patch
  Adds gfx1310 as its own AMD ISA family in the vendored Triton backend, so
  that Rock can tell gfx13 apart from GFX1250 when it queries the Triton
  target. Four changes only: the ISAFamily::GFX1310 enumerator, a
  major == 13 && minor == 1 arm in getISAFamily() (gfx1310 numbering, not
  every gfx13* chip), a GFX1310 case in isRDNA(), and GFX1310 grouped with
  RDNA4 in supportsBufferAtomicFadd() (no BUFFER_ATOMIC_ADD_F64, matching
  FeatureISAVersion13 in public LLVM).

  This change is deliberately the identity slice and nothing more.

  Drop when upstream Triton carries gfx1310 natively.

patch-partitionloops-clang-cl.patch
  Upstream PR: https://github.com/triton-lang/triton/pull/11114
  Upstream title: Fix getPartition overload ambiguity with clang-cl
  Changes
  partitions.getPartition((int)0) to partitions.getPartition(0u) in
  lib/Dialect/TritonGPU/Transforms/WarpSpecialization/PartitionLoops.cpp.
  `(int)0` is also a null-pointer constant, so under clang-cl the call is
  ambiguous between getPartition(unsigned) and getPartition(Operation*); an
  explicitly unsigned literal selects the intended getPartition(unsigned)
  overload. No-op for GCC/Clang on Linux, which resolve the overload fine.
  Keep until the vendored Triton revision contains the upstream fix.

patch-targetfeatures-msvc-c4715.patch
  Adds an llvm_unreachable after the fully covered ISAFamily switch in
  TargetFeatures::supportsBufferAtomicFadd, so the function has a return on
  every path as far as cl.exe is concerned. Clang proves the switch
  exhaustive and stays quiet; MSVC does not and emits C4715 ("not all control
  paths return a value"), which is fatal under /WX. Placing the statement
  after the switch rather than in a `default:` keeps -Wcovered-switch-default
  satisfied on the Clang side and preserves the -Wswitch coverage that a
  `default:` would defeat, so a Triton bump adding a new ISAFamily still
  fails the build rather than falling through silently.

  No behavioural change on any toolchain: the statement is unreachable.

  Stacks on patch-buffer-atomics.patch and must be applied after it: that
  patch is what rewrites supportsBufferAtomicFadd into a switch in the first
  place. Upstream main-windows has no switch here at all -- it is an if-chain
  ending in an unconditional `return true;` -- so there is nothing to upstream
  and no bump will ever make this redundant on its own. Drop it together with
  patch-buffer-atomics.patch, whose own upstreaming was already rejected in
  https://github.com/triton-lang/triton/pull/10408.

patch-buffer-atomics.patch
  Enables buffer atomic RMW across all AMD GPU families in
  TargetFeatures::supportsBufferAtomicRMW (gfx906/gfx908/gfx90a/gfx942/gfx950,
  gfx101x/gfx103x/gfx11/gfx12, gfx1250). On older families BUFFER_ATOMIC_*
  silently drops writes against fine-grained pinned host memory, but
  rocmlirTriton never targets such allocations so this is safe.
  Integer RMW works universally; the per-family FP restrictions for
  BUFFER_ATOMIC_ADD_{F32,F64}/PK_ADD_{F16,BF16} are encoded in
  supportsBufferAtomicFadd (e.g. gfx906/gfx101x/gfx103x have no FP buffer
  atomic add; gfx11 only F32; gfx942 no PK_ADD_BF16; gfx12 no F64).
  Upstreaming was attempted in https://github.com/triton-lang/triton/pull/10408
  but it was rejected.
  Enabling RMW on RDNA3/GFX1170 also makes f32 buffer atomic fmin/fmax reachable
  there, so patch11018 lists those rows of
  test/TritonGPU/amd/amd-convert-buffer-ops-atomic-fminmax.mlir as BUF-F32.

patch-wmma-preserve-discardable-attrs.patch
  Lets rocmlirTriton choose the WMMA result transposition downstream instead
  of inside Triton.

  rocmlirTriton computes a `rock.o_transposed` discardable attribute at the
  rock level (rock-add-triton-metadata, run right after rock-lower-stores,
  using the store destination's getMaxVectorization), carries it onto the
  lowered tt.dot/tt.dot_scaled (RockToTTIR), and finally consumes it after
  accelerate-matmul (rock-set-matmul-output-transpose) to set the WMMA
  isTransposed flag so the epilogue store coalesces.

  This patch is the small piece that has to live inside Triton: it makes
  AccelerateAMDMatmul copy the discardable attributes from the original dot
  onto every freshly-created accelerator dot (MFMA / WMMA / scaled / v_dot /
  FMA paths) so downstream metadata such as `rock.o_transposed` survives the
  rewrite. It adds no Triton-side decision logic; the orientation is chosen
  by the downstream rock pass.

patch-float-atomic-minmax-lowering.patch
  Fixes Triton atomic max/min lowering for floating-point element types. The
  shared matchAtomicOp helper now receives the value type and maps floating
  MAX/MIN operations to LLVM `fmax` / `fmin` rather than integer max/min; the
  AMD intra-wave reduction path handles those new floating atomic binops.

patch-preserve-arith-bitcast-lowering.patch
  Keeps `arith.bitcast` legal through Triton's Triton-to-TritonGPU and
  TritonGPU-to-LLVM conversion pipeline by adding the corresponding generic
  conversion and LLVM lowering patterns.

patch-roundeven-lowering.patch
  Keeps tensor `math.roundeven` legal through Triton's
  Triton-to-TritonGPU conversion and scalarizes it to the LLVM
  `llvm.intr.roundeven` intrinsic. This lets TOSA float-to-integer casts retain
  round-to-nearest-even semantics and lower to the target's native rounding
  instruction instead of an expanded arithmetic sequence.

patch-skip-subbyte-reduce-data-duplication.patch
  Prevents ReduceDataDuplication from materializing sub-byte tensors through
  local memory. Triton's convert-layout lowering already widens these transfers
  to i8 and truncates back to the logical element type, so introducing local
  memory here is incorrect for sub-byte element types.

patch-gfx1170.patch
  Adds gfx1170 (ISA 11.7) as its own ISAFamily::GFX1170 in the vendored Triton
  AMD backend. gfx1170 is a gfx11/RDNA3-based core (wave32, RDNA3 memory model,
  RDNA3 buffer/cache encoding) that ships the gfx12/RDNA4 matrix engine
  (128-bit WMMA v2 + SWMMAC, fp8 conversion insts, IEEE min/max), so it is
  classified before the generic gfx11 -> RDNA3 catch-all in
  TargetFeatures::getISAFamily and then treated as RDNA3 for memory-model
  pieces (buffer atomics, cache-modifier bits, shared ld/st tiles) but as
  RDNA4 for the matrix engine (getWmmaVersion -> v2, supportMaximumMinimum,
  scaled-blocked decomposition). Also wires gfx117 into compiler.py
  is_in_thread_transpose_enabled and adds RDNA3/gfx1170 lit coverage. Carries
  TODO(gfx1170) notes (fp8 OCP HW cvt in ConvertFpCastOpToLLVM, i4 WMMA)
  documenting latent perf gaps that are correct via the software/upcast
  fallback today.

  Also implements the fp8 dot4 FMA path that gfx1170 and RDNA4 share.
  TargetFeatures::supportsFp8Dot4Fma gates {GFX1170, RDNA4}, isLegalFMAForm
  admits fp8/bf8 operand pairs with k % 4 == 0, and DotOpToLLVM/FMA selects the
  matching llvm.amdgcn.dot4.f32.{fp8,bf8}.{fp8,bf8} for all four pairings.
  A and B may differ, since each ordering has its own instruction.

  The path is not reachable through accelerate-matmul today: BlockedToWMMA
  claims every fp8 dot on these targets except K == 1, and K == 1 in turn fails
  the k % 4 == 0 requirement. Unlike MFMA, which declines on
  inputKSize % kDim != 0 and hands off to FMA, WMMA has no K-divisibility guard,
  so the whole packed-dot FMA family (f16 fdot2, i8 sdot4, fp8 dot4) is latent
  on WMMA targets. Coverage is therefore at the Conversion level rather than end
  to end: test/Conversion/amd/fp8_dot4.mlir feeds blocked fp8 dots straight into
  --convert-triton-amdgpu-to-llvm on gfx1170 and gfx1200, pinning all four
  FP8/BF8 operand pairings.

  The WMMA v2 conversion regression also covers all four OCP fp8/bf8 operand
  combinations and their exact LLVM intrinsics.

  The `test/Conversion/amd/warp_id_to_llvm.mlir` hunk stacks on
  patch-warp-id-readfirstlane.patch and must be applied after it: it adds a
  gfx1170 RUN line against the `ARITH`/`WAVEID` prefixes that
  https://github.com/triton-lang/triton/pull/11570 introduced, so applied
  first, against the older `GFX9`/`GFX12` prefixes, it rejects. Once a bump
  pulls in that upstream PR the readfirstlane record is dropped and this hunk
  applies to plain upstream on its own.

  Drop this patch on the next Triton bump that pulls gfx1170 support upstream
  into external/triton.

patch11486.patch
  Upstream PR: https://github.com/triton-lang/triton/pull/11486
  Upstream title: [AMD] Use hardware cvt instructions for OCP fp8 casts on
  gfx1170

  Applies on top of patch-gfx1170.patch and uses the hardware OCP fp8/bf8
  conversion instructions on gfx1170. gfx1170 has FeatureFP8ConversionInsts,
  i.e. the *unscaled* v_cvt_f32_{fp8,bf8} / v_cvt_pk_{fp8,bf8}_f32 ops, and on
  it those ops read and write the OCP encoding -- the same instructions CDNA3
  uses for FNUZ, the target decides the format. It lacks the scaled
  v_cvt_scalef32_pk_* ops that CDNA4 and gfx1250 use. ConvertFpCastOpToLLVM
  gains a hasUnscaledOcpFp8Cvt({GFX1170}) capability and routes these OCP
  casts on it to hardware instead of the software bit-manipulation fallback:
  - f32/f16/bf16 -> f8E4M3FN/f8E5M2 (RTNE) reuse the existing unscaled
    downcast helpers shared with CDNA3 FNUZ, with "fnuz" dropped from their
    names (Fp32ToFp8E4M3HW, Fp16ToFp8E5M2HW, Bf16ToFp8E4M3HW, ...). f16/bf16
    widen to f32 first, which is exact.
  - f8E4M3FN/f8E5M2 -> f32 use the new F8x4ToFp32 helper: one
    v_cvt_f32_{fp8,bf8} per byte, byte_sel 0-3, over a packed dword.
    createDestOps no longer routes this through an f16 intermediate on
    gfx1170.
  - f8 -> f16/bf16 upcasts and RTZ downcasts stay on the software path.
  The packed upcast v_cvt_pk_f32_{fp8,bf8} is avoided because LLVM selects
  its fake16 form and prints it without the .l/.h suffix the gfx12 assembler
  demands in real-true16 mode (LCOMPILER-2609). Also adds a gfx1250
  fp8 -> f32 check to tritongpu_to_llvm_gfx1250.mlir, and deletes
  test/Conversion/amd/fp_to_fp_gfx1170.mlir from patch-gfx1170.patch, which
  pinned the software fallback this patch replaces;
  test/Conversion/amd/ocp_fp8_cvt_lowering.mlir covers the same casts.

  Differs from upstream only where the pinned Triton does:
  - Upstream calls gfx1170's family ISAFamily::RDNA4m; here it is
    ISAFamily::GFX1170 (patch-gfx1170.patch).
  - The pinned ConvertFpCastOpToLLVM still uses free-function ConverterT
    dispatchers rather than upstream's ConverterInterface classes, so the
    routing is in those dispatchers: Fp8E4M3fnToFp32 / Fp8E5M2ToFp32 become
    ISA-dependent (the CDNA4+ bodies move to *ToFp32HW), and the renamed
    unscaled helpers are forward-declared.
  - Upstream's rename turns Bf16ToFp8E5M2fnuzHW into Bf16ToFp8E5M2HW, which
    here was already taken by the CDNA4 scaled converter. That converter is
    renamed Bf16ToFp8E5M2rtneHW, matching Fp16ToFp8E5M2rtneHW and
    Fp32ToFp8E5M2rtneHW.
  - Upstream's CvtFp8E4M3ToFp32::getNumElements fix is a merge bug in
    upstream's class layout and has no counterpart here.

  mlir/test/rocmlir-driver/{fp8,bf8}_cvt_lowering.mlir check the result end
  to end: on gfx1170 rocdl.cvt.f32.{fp8,bf8} and rocdl.cvt.pk.{fp8,bf8}.f32
  reach v_cvt_f32_* / v_cvt_pk_*_f32 in the ISA, with no packed upcast.

  Drop this patch on the next Triton bump that includes upstream merge commit
  fa2e589b55706d0de73d25641840e134f20a2c65.

patch10635.patch
  Fixes AMD software pipelining for undersized direct-to-LDS tiles. The
  pipeliner's async-copy eligibility check now first applies Triton's standard
  `triton::canBeConvertedToAsyncLoad` contiguity/alignment check, then rejects
  scatter-less direct-to-LDS targets when the CTA tile does not contain enough
  data for each warp lane to write at least 32 bits into LDS
  (`hasEnoughCTABytesForDirectToLds`, `ctaTileBits >= 32 * warpSize`). This
  keeps undersized tiles on the register path instead of creating async copies
  that later fail direct-to-LDS lowering. Mirrors upstream Triton PR
  https://github.com/triton-lang/triton/pull/10635 exactly.

  Drop this patch on the next Triton bump that pulls PR #10635 (upstream main at
  f12e94d or later) into external/triton.

patch10928.patch
  Supports a blocked/shared order mismatch for direct-to-LDS loads on gfx9.
  When the blocked and shared encodings have different orders, the srcToShared
  layout has contig=1 (smaller than the blocked encoding), so CoalesceAsyncCopy
  either skipped rewriting the blocked encoding or rewrote it incorrectly,
  yielding non-coalesced LDS writes. The pass now detects when the layout
  restricts contiguity below the load contiguity and always rewrites the src
  layout, distributing lanes/warps along the shared order while keeping the
  original blocked order for the final encoding. The lowering
  (canLoadDirectToLDS) also no longer bails out when the pointer contiguity
  exceeds the srcToShared contiguity: instead it clamps the load width down to
  the coalesced chunk size and splits the load into multiple narrower
  direct-to-LDS ops. Mirrors upstream Triton PR
  https://github.com/triton-lang/triton/pull/10928 exactly.

  Drop this patch on the next Triton bump that pulls PR #10928 into
  external/triton.

patch11018.patch
  Gates buffer atomic float min/max on native hardware support:
  ConvertToBufferOps only rewrites tt.atomic_rmw max/min into
  amdg.buffer_atomic_rmw when TargetFeatures::supportsBufferAtomicFMinMax
  accepts the target/type pair (f32 on RDNA1/RDNA2/RDNA3/RDNA4m/RDNA4/GFX1250,
  f64 on CDNA2/CDNA3/CDNA4/RDNA1/RDNA2/GFX1250); integer min/max always take the
  generic path.
  Buffer atomics never reach AtomicExpandPass, so a missing instruction (f32 on
  CDNA) used to be an ISel failure, while the generic atomicrmw fmax/fmin
  fallback always has a CAS expansion. That is what lets rocMLIR drop its
  isFastAtomicMaxSupported() fusion gate.
  The gfx1100 and gfx1170 rows of the test matrix use BUF-F32 where upstream uses
  NO-F32: upstream reaches those families with no buffer atomic RMW at all, while
  patch-buffer-atomics enables it and GFX11 does carry
  AtomicFMinFMaxF32GlobalInsts.

  Imports https://github.com/triton-lang/triton/pull/11018 (merged form), minus
  the LoadStoreOpToLLVM.cpp hunk, which patch-float-atomic-minmax-lowering.patch
  already covers centrally in matchAtomicOp. Lit coverage lives in
  amd-convert-buffer-ops-atomic-fminmax.mlir as upstream does, leaving
  amd-convert-buffer-ops.mlir unchanged. Upstream names gfx1170 ISAFamily::RDNA4m;
  this tree uses ISAFamily::GFX1170 (patch-gfx1170.patch) at the same list slot.

  Drop on the next Triton bump that pulls PR #11018.

patch-free-var-mask-register-dim-name.patch
  Names the register dimension "register" everywhere free-variable masks are
  produced and consumed, so the redundant-register guards actually fire.

  getFreeVariableMasks(Type) keyed that dimension "reg" for scalars but
  "register" for tensors, since LinearLayout keys by its input dimension names.
  Every consumer used "reg", so on tensors the lookup missed and
  MapVector::operator[] default-inserted 0, making isCanonicalIndex() always
  true and leaving every redundant-element guard as dead code. Fixed here for
  the producer and for every consumer: the AMD and NVIDIA store, atomic RMW and
  CAS conversions, AMD's isRedundantThreadPredWarpUniform, and GSan's
  instrumentation. Scalars read the same all-redundant mask as before, so only
  tensor layouts change behaviour.

  It matters for layouts that broadcast across registers: gfx11 WMMA duplicates
  its result rather than offsetting it, so a depthwise convolution tuned to
  mPerBlock = 1 stored the same element from all 8 registers of a lane. On the
  yolov10n depthwise shapes gfx1100 emitted 32 stores and 32 exp2 calls instead
  of 4 and 4, measuring 1.12x-2.00x slower.

  Not filed upstream yet; upstream Triton has the same defect.

patch-cost-aware-dot-rematerialization.patch
  Upstream PR: https://github.com/triton-lang/triton/pull/11551
  Upstream title: [TRITONGPU] Avoid expensive math rematerialization when
  hoisting dot operands
  Stops LayoutRematerialization::hoistConvertDotOperand from rematerializing
  expensive math. The pass moved every ttg.convert_layout next to its load once
  the backward slice was elementwise-pure, even when the slice had to be
  duplicated or ran in a dot-operand layout that replicates the operand across
  warps, multiplying transcendental work.
  Mirrors the upstream PR: the cost computation is split into getSliceOps,
  getValuesUsedOutsideSlice and getRematerializationCost, which reports
  totalCost, expensiveMathCost and splitsSlice, and the hoist is rejected only
  when expensiveMathCost is non-zero. Cheap elementwise chains still hoist,
  because the payoff there is pipelining the loads rather than a cheaper
  convert. test/TritonGPU/amd/remove-layout-conversions-dot-operand-cost.mlir is
  byte-identical to the version in that PR.
  Two deviations from the PR, both because the pinned Triton predates the
  feature: isRematBeneficial keeps its four-parameter signature and the
  disableRematSplitting rejection is omitted. The splitsSlice field is kept so
  the next bump can drop this record without further edits.
  An earlier revision of this record gated on total cost instead, which also
  suppressed cheap chains and left five sections of test/TritonGPU/combine.mlir
  and all three functions of
  test/TritonGPU/amd/accelerate-amd-matmul-mfma-decompose-scaled-dot.mlir
  failing; both are untouched upstream tests and now pass unmodified. That
  revision also declared 21 new lines in a hunk with 20, so it could not be
  reverse-applied in Step 1.2 of docs/bump_triton_version.md.

  Motivation: fused elementwise + conv kernels on RDNA (e.g. log/tanh/mul on
  the B operand before a WMMA dot) regressed ~15% vs rocMLIR because a
  single-M-tile tuning config left the input chain rematerialized in a
  replicated WMMA dot-operand layout. Keeping the convert after the expensive
  chain lets each warp compute once and store to LDS.

  Drop this record once the upstream PR lands and the vendored Triton contains
  it. If the expensive-math policy turns out to be too weak or too strong for
  dot-operand hoists, tune getCostFactor or the expensive-math multiplier in one
  place rather than adding a second heuristic.

patch-negligible-anchor-layout-conflict.patch
  Adds the tie-break that LayoutPropagation::resolveConflicts asked for in its
  "hacky resolve" comment. Each anchor carries the traffic its layout governs,
  the figure propagates with the layout, and a candidate whose anchor governs
  no more than one dword per thread loses to one that governs more. The
  type-based preference still decides first.

  The 128x1 bias load left behind by rock-narrow-redundant-loads still anchors
  by element count, and with no mma candidate yet before accelerate-matmul,
  iteration order handed the whole epilogue of the dot that load's
  sizePerThread = [1, 1] layout and a full-tile shared-memory round trip: up
  to 1.6x slower on gfx1100 convolution+reduce fusions. Ranking every conflict
  by traffic was tried too and regressed other configs, as getConvertCost
  prices the register permutes it trades for at zero.

  No upstream PR yet. Covered by
  test/TritonGPU/amd/remove-layout-conversions-negligible-anchor.mlir and, for
  the interaction with the Rock pass, by the rocMLIR test
  Dialect/Rock/narrow-redundant-loads-through-triton.mlir.

patch-optimize-epilogue-rock-metadata.patch
  Makes OptimizeEpilogue honor the discardable `rock.prefer_lds_epilogue`
  function marker. Marked kernels keep the paced LDS round-trip instead of
  using BypassEpilogueSMEM's register permlane bypass. The store-tail heuristic
  and tri-state policy resolution live in rocMLIR's rock-add-triton-metadata
  pass; no Rock-specific performance model remains in the vendored Triton
  implementation.

patch-optimize-epilogue-fma-blocked.patch
  Lets BypassEpilogueSMEM also bypass the epilogue relayout when the dot
  accumulator carries a blocked (FMA) layout, not just an WMMA/MFMA one.
  This shows perf improvement in some kernels.

  Stacks on patch-optimize-epilogue-rock-metadata.patch; apply it after that
  one. Plan is to upstream this PR.

patch11295.patch
  Fixes a GFX9 direct-to-LDS miscompile that faults at runtime. The lowering
  implements a swizzled shared encoding as a within-warp lane shuffle to
  `laneId + swizzleLaneOffset`, assuming that lands in [0, warpSize), but a
  wide operand swizzle can have a reach of `vec * maxPhase` larger than the
  lanes covering the swizzled dimension, so the shuffle crosses the warp
  boundary and issues an out-of-bounds global read.
  Once a load passes final async-copy eligibility, createStreamOps halves the
  candidate encoding's maxPhase until the shuffle is provably in-warp, and
  keeps the clamp only if the load remains async-copy eligible afterward.
  This keeps the direct-to-LDS fast path with its vectorization intact at the
  cost of some bank-conflict avoidance, while ineligible stream copies retain
  their original encoding.

  Tracks https://github.com/triton-lang/triton/pull/11295. Drop this patch once
  the pinned Triton revision includes that change.

patch-direct-to-lds-swizzle-check-vec.patch
  Measures the direct-to-LDS lane shuffle with the load's vector rather than
  the shared encoding's, so the clamp patch11295.patch added fires when it
  should.

  emitSwizzledLaneOffsets turns the swizzled-vs-flat offset delta into a lane
  offset by dividing by the vector the load uses, which canLoadDirectToLDS sets
  to the register-to-shared run. swizzlesInsideWarp divided by enc.getVec()
  instead, which is larger whenever the shared tile is wider than one load, so
  the displacement looked smaller than it is and a shuffle that leaves the warp
  passed as in-warp. The check now takes the vector createStreamOps hands to
  createAsyncCopy, from the pointer contiguity and the mask alignment, and caps
  it the way CoalesceAsyncCopy does, by the register-to-shared run and by the
  widths the target can write to LDS.

  The dot-operand hoist from triton#11551 reaches this with f32 tiles carrying
  the dot-operand layout of a bf16 dot, kWidth = 8 against a load vector of a
  single f32, since CDNA4 writes only 32 and 128 bits to LDS. With that port
  applied, ROCK E2E PrGemm/pr_gemm_1_2.mlir (f32 gemm, k = 769) read from a lane
  outside its warp and got half its output wrong.

  Stacks on patch11295.patch and must be applied after it.

  Not filed upstream yet; upstream PR 11295 carries the same mismatch.

patch-elementwise-fastmath-flags.patch
  Carries fast-math flags across the dialect boundary in the elementwise
  lowering, which otherwise drops them. arith and math declare `fastmath` as
  an inherent attribute, so it lives in the operation's properties and is
  absent from the dictionary an adaptor forwards; LLVM spells the same flags
  as `fastmathFlags`, so even an explicit copy would land inert.
  Adds getArithFastmathFlags / getLLVMFastmathFlags /
  propagateFastMathFlags to ElementwiseOpToLLVMBase.h (hence the new
  MLIRArithAttrToLLVMConversion link dependency), calls
  propagateFastMathFlags from the generic ElementwiseOpConversion, and
  threads the translated attribute through the AMD add/sub/mul/div
  conversions -- including the bf16 pairs routed via
  EmitDualBF16ElementwiseOp -- and the exp expansion.

  This is inert for upstream Triton, whose frontend never sets fast-math
  flags: every helper returns a null attribute and each destination operation
  is built exactly as before. It matters downstream because
  `rock-allow-fast-math-flags` tags arith and math ops before they cross into
  Triton, and losing the flags at the boundary costs real code quality -- most
  visibly `arith.divf`, which without `arcp` lowers to the IEEE division fixup
  sequence rather than a bare reciprocal.

  Not yet proposed upstream. Keep until Triton forwards these flags itself.

patch-warp-id-readfirstlane.patch
  Emits `rocdl.readfirstlane` on every target that lowers `ttg.warp_id` through
  the thread-id arithmetic path, not just CDNA3/CDNA4. `warpId` is derived from
  `workitem.id.x`, so LLVM's uniformity analysis treats it as divergent even
  though every lane in a wave computes the same value; the readfirstlane moves
  it into an SGPR and lets uniformity propagate to dependent ops, which pick
  SALU/SGPRs instead of VALU/VGPRs.

  Available on every family we support: `v_readfirstlane_b32` has existed
  since gfx6, and neither `int_amdgcn_readfirstlane`, the `GCNPat` that
  selects it, nor the `V_READFIRSTLANE_B32` pseudo carries a
  `SubtargetPredicate` -- the real encodings span gfx6/gfx7, the gfx8/gfx9
  "vi" family, and gfx10/11/12/13. Reading lane 0 is an identity rather than
  an approximation, because `tid / warpSize` is wave-uniform by construction.
  Only families without a hardware wave id reach this code, so RDNA4 and
  GFX1250 are unaffected and CDNA3/CDNA4 are unchanged; GCN5_1, CDNA1, CDNA2,
  RDNA1, RDNA2, RDNA3, and GFX1170 are what newly gain the readfirstlane.

  Upstream PR: https://github.com/triton-lang/triton/pull/11570

patch-fma-lds-swizzle.patch
  Swizzles the pipelined LDS tile for FMA dot operands, which
  composePaddedLayout does not cover and upstream leaves unswizzled.
  SwizzledSharedEncodingAttr::get returns vec = 1, perPhase = 1, maxPhase = 1
  whenever the dot's parent layout is not MFMA/WMMA/Nvidia MMA, and
  composePaddedLayout only covers CDNA4 MFMA and gfx1250 WMMA, so an f32 dot on
  a target without a matrix core gets no swizzle at all.
  getSharedEncIfAllUsersAreDotEnc gains composeSwizzledLayoutForFMA, called for
  blocked-parent operands after composePaddedLayout declines and before the
  generic dot-operand constructor. The helper accounts for target bank count
  and rows narrower than a complete bank row. It is limited to f32 because
  other FMA element types use different packed LDS access patterns.

  Stacks on patch10694.patch and must be applied after it: the shared orders
  expected in test/TritonGPU/amd/amd-pipeline-fma-lds-swizzle.mlir are the
  operand-major ones that patch introduces.

  Not filed upstream yet; upstream Triton has the same performance gap.

patch11890.patch
  composePaddedLayoutForAsyncCopyCDNA4 divides warpSize by contigLanes, the
  number of 16-byte vectors in one row of the tile, to get the rows one warp
  covers. Once a row spans more than a warp of vectors that quotient truncates
  to zero, so requiredRows collapses, xWayConflicts always reports one, and the
  useBestWrap guard degenerates to nonContigDim >= 0. wrap then exceeds the
  rows the tile has, bases are added for rows that do not exist, and the
  resulting layout broadcasts in the offset dimension, which
  PaddedSharedEncodingAttr::verify rejects. In an assertions build that aborts
  the compiler instead of falling back.

  The weekly tuning stage hit this on gfx950 for gemm f16 m=384 k=3072 n=768
  with mPerBlock=1, nPerBlock=16, kPerBlock=2048, where contigLanes is 256
  against a warp size of 64. contigLanes is now clamped to [1, warpSize], so a
  warp counts as covering one row when a row is wider than a warp, and a row
  narrower than a vector can no longer make it zero.

  Across 70 shape and dtype combinations this takes process aborts from 8 to 0
  and keeps the 55 shapes that already compiled bit identical. The lit test
  test/TritonGPU/amd/amd-pipeline-padded-layout-wide-row-gfx950.mlir uses a
  4-row tile, fewer rows than the stagger, and
  mlir/test/fusion/pr-e2e/rock-gemm-cdna4-padded-layout-wide-row.mlir runs the
  weekly config end to end on gfx950. The downstream copy of the lit test
  carries the MIT header required for files added by local [EXTERNAL]
  commits; the upstream copy has none.

  Imports https://github.com/triton-lang/triton/pull/11890.

  Drop this patch on the next Triton bump that includes upstream merge commit
  1725224a65ebc2dc7ca2ee1d84458344d93ee797.

patch-gfx1310-isa-family.patch
  Adds gfx1310 as its own AMD ISA family in the vendored Triton backend, so
  that Rock can tell gfx13 apart from GFX1250 when it queries the Triton
  target. Four changes only: the ISAFamily::GFX1310 enumerator, a
  major == 13 && minor == 1 arm in getISAFamily() (gfx1310 numbering, not
  every gfx13* chip), a GFX1310 case in isRDNA(), and GFX1310 grouped with
  RDNA4 in supportsBufferAtomicFadd() (no BUFFER_ATOMIC_ADD_F64, matching
  FeatureISAVersion13 in public LLVM).

  This change is deliberately the identity slice and nothing more.

  Drop when upstream Triton carries gfx1310 natively.

patch-partitionloops-clang-cl.patch
  Upstream PR: https://github.com/triton-lang/triton/pull/11114
  Upstream title: Fix getPartition overload ambiguity with clang-cl
  Changes
  partitions.getPartition((int)0) to partitions.getPartition(0u) in
  lib/Dialect/TritonGPU/Transforms/WarpSpecialization/PartitionLoops.cpp.
  `(int)0` is also a null-pointer constant, so under clang-cl the call is
  ambiguous between getPartition(unsigned) and getPartition(Operation*); an
  explicitly unsigned literal selects the intended getPartition(unsigned)
  overload. No-op for GCC/Clang on Linux, which resolve the overload fine.
  Keep until the vendored Triton revision contains the upstream fix.

patch-buffer-atomics.patch
  Enables buffer atomic RMW across all AMD GPU families in
  TargetFeatures::supportsBufferAtomicRMW (gfx906/gfx908/gfx90a/gfx942/gfx950,
  gfx101x/gfx103x/gfx11/gfx12, gfx1250). On older families BUFFER_ATOMIC_*
  silently drops writes against fine-grained pinned host memory, but
  rocmlirTriton never targets such allocations so this is safe.
  Integer RMW works universally; the per-family FP restrictions for
  BUFFER_ATOMIC_ADD_{F32,F64}/PK_ADD_{F16,BF16} are encoded in
  supportsBufferAtomicFadd (e.g. gfx906/gfx101x/gfx103x have no FP buffer
  atomic add; gfx11 only F32; gfx942 no PK_ADD_BF16; gfx12 no F64).
  Upstreaming was attempted in https://github.com/triton-lang/triton/pull/10408
  but it was rejected.

patch10498.patch
  Extends patch10450's soffset-split safety check to peel sign-preserving
  transparent wrappers (splat/broadcast/expand_dims/reshape/convert_layout)
  before trusting the integer-range lattice, so an offset of the form
  convert_layout(add(base, <negative>)) is no longer wrongly annotated
  split-safe. Applies on top of patch10450. Mirrors upstream Triton PR
  https://github.com/triton-lang/triton/pull/10498 exactly.

patch10585.patch
  Fixes a case where the block ping pong schedule was wrongly being applied
  in situations where it was not safe to do so because of non-uniform masks.
  
patch-wmma-preserve-discardable-attrs.patch
  Lets rocmlirTriton choose the WMMA result transposition downstream instead
  of inside Triton.

  rocmlirTriton computes a `rock.o_transposed` discardable attribute at the
  rock level (rock-add-triton-metadata, run right after rock-lower-stores,
  using the store destination's getMaxVectorization), carries it onto the
  lowered tt.dot/tt.dot_scaled (RockToTTIR), and finally consumes it after
  accelerate-matmul (rock-set-matmul-output-transpose) to set the WMMA
  isTransposed flag so the epilogue store coalesces.

  This patch is the small piece that has to live inside Triton: it makes
  AccelerateAMDMatmul copy the discardable attributes from the original dot
  onto every freshly-created accelerator dot (MFMA / WMMA / scaled / v_dot /
  FMA paths) so downstream metadata such as `rock.o_transposed` survives the
  rewrite. It adds no Triton-side decision logic; the orientation is chosen
  by the downstream rock pass.

patch-float-atomic-minmax-lowering.patch
  Fixes Triton atomic max/min lowering for floating-point element types. The
  shared matchAtomicOp helper now receives the value type and maps floating
  MAX/MIN operations to LLVM `fmax` / `fmin` rather than integer max/min; the
  AMD intra-wave reduction path handles those new floating atomic binops.

patch-preserve-arith-bitcast-lowering.patch
  Keeps `arith.bitcast` legal through Triton's Triton-to-TritonGPU and
  TritonGPU-to-LLVM conversion pipeline by adding the corresponding generic
  conversion and LLVM lowering patterns.

patch-roundeven-lowering.patch
  Keeps tensor `math.roundeven` legal through Triton's
  Triton-to-TritonGPU conversion and scalarizes it to the LLVM
  `llvm.intr.roundeven` intrinsic. This lets TOSA float-to-integer casts retain
  round-to-nearest-even semantics and lower to the target's native rounding
  instruction instead of an expanded arithmetic sequence.

patch-skip-subbyte-reduce-data-duplication.patch
  Prevents ReduceDataDuplication from materializing sub-byte tensors through
  local memory. Triton's convert-layout lowering already widens these transfers
  to i8 and truncates back to the logical element type, so introducing local
  memory here is incorrect for sub-byte element types.

patch-gfx1170.patch
  Adds gfx1170 (ISA 11.7) as its own ISAFamily::GFX1170 in the vendored Triton
  AMD backend. gfx1170 is a gfx11/RDNA3-based core (wave32, RDNA3 memory model,
  RDNA3 buffer/cache encoding) that ships the gfx12/RDNA4 matrix engine
  (128-bit WMMA v2 + SWMMAC, fp8 conversion insts, IEEE min/max), so it is
  classified before the generic gfx11 -> RDNA3 catch-all in
  TargetFeatures::getISAFamily and then treated as RDNA3 for memory-model
  pieces (buffer atomics, cache-modifier bits, shared ld/st tiles) but as
  RDNA4 for the matrix engine (getWmmaVersion -> v2, supportMaximumMinimum,
  scaled-blocked decomposition). Also wires gfx117 into compiler.py
  is_in_thread_transpose_enabled and adds RDNA3/gfx1170 lit coverage. Carries
  TODO(gfx1170) notes (fp8 OCP HW cvt in ConvertFpCastOpToLLVM, i4 WMMA)
  documenting latent perf gaps that are correct via the software/upcast
  fallback today.

  Also implements the fp8 dot4 FMA path that gfx1170 and RDNA4 share.
  TargetFeatures::supportsFp8Dot4Fma gates {GFX1170, RDNA4}, isLegalFMAForm
  admits fp8/bf8 operand pairs with k % 4 == 0, and DotOpToLLVM/FMA selects the
  matching llvm.amdgcn.dot4.f32.{fp8,bf8}.{fp8,bf8} for all four pairings.
  A and B may differ, since each ordering has its own instruction.

  The path is not reachable through accelerate-matmul today: BlockedToWMMA
  claims every fp8 dot on these targets except K == 1, and K == 1 in turn fails
  the k % 4 == 0 requirement. Unlike MFMA, which declines on
  inputKSize % kDim != 0 and hands off to FMA, WMMA has no K-divisibility guard,
  so the whole packed-dot FMA family (f16 fdot2, i8 sdot4, fp8 dot4) is latent
  on WMMA targets. Coverage is therefore at the Conversion level rather than end
  to end: test/Conversion/amd/fp8_dot4.mlir feeds blocked fp8 dots straight into
  --convert-triton-amdgpu-to-llvm on gfx1170 and gfx1200, pinning all four
  FP8/BF8 operand pairings.

  The WMMA v2 conversion regression also covers all four OCP fp8/bf8 operand
  combinations and their exact LLVM intrinsics.

  The `test/Conversion/amd/warp_id_to_llvm.mlir` hunk stacks on
  patch-warp-id-readfirstlane.patch and must be applied after it: it adds a
  gfx1170 RUN line against the `ARITH`/`WAVEID` prefixes that
  https://github.com/triton-lang/triton/pull/11570 introduced, so applied
  first, against the older `GFX9`/`GFX12` prefixes, it rejects. Once a bump
  pulls in that upstream PR the readfirstlane record is dropped and this hunk
  applies to plain upstream on its own.

  Drop this patch on the next Triton bump that pulls gfx1170 support upstream
  into external/triton.

patch-gfx1170-fp8-cvt.patch
  Applies on top of patch-gfx1170.patch and uses the hardware OCP fp8/bf8
  conversion instructions on gfx1170. gfx1170 and RDNA4 have
  FeatureFP8ConversionInsts, i.e. the *plain*
  v_cvt_pk_f32_{fp8,bf8} / v_cvt_pk_{fp8,bf8}_f32 ops, and on them those ops
  read and write the OCP encoding -- unlike CDNA3, where the same mnemonics
  mean FNUZ, which is why the existing plain converters could not simply be
  reused. They also lack the scaled v_cvt_scalef32_pk_* ops that CDNA4 and
  gfx1250 use, so the CDNA4 OCP converters could not be reused either.
  ConvertFpCastOpToLLVM therefore gains a hasPlainOcpFp8HW({GFX1170})
  capability and a plain-hardware branch in each of the twelve OCP fp8
  dispatchers, replacing the software bit-manipulation fallback. Those twelve
  branches share two helpers, plainHWUpcastFromFp8 and plainHWDowncastToFp8,
  parameterized by the f32/f16/bf16 type on the non-fp8 side. There is no
  plain 16-bit-source op, so f16/bf16 casts hop through f32; both hops are
  lossless for these value ranges, leaving the hardware op as the single
  rounding site. createDestOps no longer forces OCP f8 -> f32 through an f16
  intermediate on these targets, since they can now do it directly.
  RTZ downcasts stay on the software path because the hardware op is
  round-to-nearest-even only, and the stochastic-rounding v_cvt_sr_* ops are
  not wired up at all: that needs an RNG operand on tt.fp_to_fp, which the
  Triton IR contract does not currently have.

  RDNA4 is deliberately left out of hasPlainOcpFp8HW even though it has the
  instructions. Its packed upcast is selected as the fake16 form of
  v_cvt_pk_f32_{fp8,bf8} and printed without the .l/.h suffix the assembler
  demands in the real-true16 mode gfx12 defaults to, so the kernel fails to
  assemble (LCOMPILER-2609). gfx11 escapes this only because make_amdgcn /
  make_hsaco pass `-real-true16` for every gfx11 kernel, which covers gfx1170.
  Add RDNA4 once LCOMPILER-2609 is fixed.

  A lone OCP fp8/bf8 value upcasting to f32 uses the scalar v_cvt_f32_{fp8,bf8}
  rather than the packed op. getNumElements returns 1 instead of the default 4
  for exactly that case on hasPlainOcpFp8HW targets, which is what stops
  createDestOps padding the value out with undef before the converter sees it;
  ScalarF8ToFp32 then emits a single ROCDL::CvtF32{Fp8,Bf8}Op with byteSel 0.
  Previously this emitted two packed converts and discarded three of the four
  results. The gate is deliberately narrow -- every other type pair keeps its
  previous element count, two-element groups still use the packed op, and
  CDNA3's FNUZ converters are untouched despite having the same shape.

  Drop this patch once gfx1170 OCP fp8/bf8 hardware conversion support is in
  the pinned Triton revision.

patch10497.patch
  Adds the RDNA FMA-dot layout rebalancing logic in AccelerateAMDMatmul, plus
  coverage for f32 FMA dots on RDNA. When WMMA cannot handle the dot, the FMA
  path rewrites imbalanced blocked layouts into a more balanced layout to
  reduce LDS read volume, then converts back to the original result layout.

patch10694.patch
  For FMA dots, re-orients the pipelined LDS tile to operand-major (M-contiguous
  for A, N-contiguous for B) in getSharedEncIfAllUsersAreDotEnc when the global
  load arrived K-contiguous. Shared order is otherwise inherited from that load,
  so an FMA operand that is transposed in global memory is read from LDS
  strided. MFMA/WMMA operands are unchanged. Imports
  https://github.com/triton-lang/triton/pull/10694.

  Drop this patch on the next Triton bump that pulls PR #10694 into
  external/triton.

patch-cost-aware-dot-rematerialization.patch
  Gates LayoutRematerialization::hoistConvertDotOperand on the existing
  isRematBeneficial cost model instead of hoisting unconditionally. The pass
  previously moved every ttg.convert_layout next to its load once the backward
  slice was elementwise-pure, even when rematerializing the slice in a
  replicated dot-operand layout cost more than keeping the convert (e.g.
  expensive math scaled by getCostFactor replication and the 8x
  isExpensiveMathOp multiplier).

  After getConvertBackwardSlice, sums getConvertCost for each load-leaf convert
  the hoist would insert and calls isRematBeneficial(convertOp, slice, layout,
  newCvtCost), matching hoistConvertOnTopOfExtOrBroadcast. Hoist proceeds only
  when eliminating the use-site convert is at least as cheap as rematerializing
  the slice plus the load-side converts.

  Motivation: fused elementwise + conv kernels on RDNA (e.g. log/tanh/mul on
  the B operand before a WMMA dot) regressed ~15% vs rocMLIR because a
  single-M-tile tuning config left the input chain rematerialized in a
  replicated WMMA dot-operand layout. Keeping the convert after the expensive
  chain lets each warp compute once and store to LDS.

  No upstream PR yet. If the shared model is too weak or too strong for dot-
  operand hoists, tune getCostFactor or the expensive-math multiplier in one
  place rather than adding a second heuristic.

  Re-evaluate on each Triton bump; drop once upstream calls isRematBeneficial
  from hoistConvertDotOperand or upstreams this change.

patch-negligible-anchor-layout-conflict.patch
  Adds the tie-break that LayoutPropagation::resolveConflicts asked for in its
  "hacky resolve" comment. Each anchor carries the traffic its layout governs,
  the figure propagates with the layout, and a candidate whose anchor governs
  no more than one dword per thread loses to one that governs more. The
  type-based preference still decides first.

  The 128x1 bias load left behind by rock-narrow-redundant-loads still anchors
  by element count, and with no mma candidate yet before accelerate-matmul,
  iteration order handed the whole epilogue of the dot that load's
  sizePerThread = [1, 1] layout and a full-tile shared-memory round trip: up
  to 1.6x slower on gfx1100 convolution+reduce fusions. Ranking every conflict
  by traffic was tried too and regressed other configs, as getConvertCost
  prices the register permutes it trades for at zero.

  No upstream PR yet. Covered by
  test/TritonGPU/amd/remove-layout-conversions-negligible-anchor.mlir and, for
  the interaction with the Rock pass, by the rocMLIR test
  Dialect/Rock/narrow-redundant-loads-through-triton.mlir.

patch-optimize-epilogue-rock-metadata.patch
  Makes OptimizeEpilogue honor the discardable `rock.prefer_lds_epilogue`
  function marker. Marked kernels keep the paced LDS round-trip instead of
  using BypassEpilogueSMEM's register permlane bypass. The store-tail heuristic
  and tri-state policy resolution live in rocMLIR's rock-add-triton-metadata
  pass; no Rock-specific performance model remains in the vendored Triton
  implementation.

patch-optimize-epilogue-fma-blocked.patch
  Lets BypassEpilogueSMEM also bypass the epilogue relayout when the dot
  accumulator carries a blocked (FMA) layout, not just an WMMA/MFMA one.
  This shows perf improvement in some kernels.

  Stacks on patch-optimize-epilogue-rock-metadata.patch; apply it after that
  one. Plan is to upstream this PR.

patch11295.patch
  Fixes a GFX9 direct-to-LDS miscompile that faults at runtime. The lowering
  implements a swizzled shared encoding as a within-warp lane shuffle to
  `laneId + swizzleLaneOffset`, assuming that lands in [0, warpSize), but a
  wide operand swizzle can have a reach of `vec * maxPhase` larger than the
  lanes covering the swizzled dimension, so the shuffle crosses the warp
  boundary and issues an out-of-bounds global read.
  Once a load passes final async-copy eligibility, createStreamOps halves the
  candidate encoding's maxPhase until the shuffle is provably in-warp, and
  keeps the clamp only if the load remains async-copy eligible afterward.
  This keeps the direct-to-LDS fast path with its vectorization intact at the
  cost of some bank-conflict avoidance, while ineligible stream copies retain
  their original encoding.

  Tracks https://github.com/triton-lang/triton/pull/11295. Drop this patch once
  the pinned Triton revision includes that change.

patch-elementwise-fastmath-flags.patch
  Carries fast-math flags across the dialect boundary in the elementwise
  lowering, which otherwise drops them. arith and math declare `fastmath` as
  an inherent attribute, so it lives in the operation's properties and is
  absent from the dictionary an adaptor forwards; LLVM spells the same flags
  as `fastmathFlags`, so even an explicit copy would land inert.
  Adds getArithFastmathFlags / getLLVMFastmathFlags /
  propagateFastMathFlags to ElementwiseOpToLLVMBase.h (hence the new
  MLIRArithAttrToLLVMConversion link dependency), calls
  propagateFastMathFlags from the generic ElementwiseOpConversion, and
  threads the translated attribute through the AMD add/sub/mul/div
  conversions -- including the bf16 pairs routed via
  EmitDualBF16ElementwiseOp -- and the exp expansion.

  This is inert for upstream Triton, whose frontend never sets fast-math
  flags: every helper returns a null attribute and each destination operation
  is built exactly as before. It matters downstream because
  `rock-allow-fast-math-flags` tags arith and math ops before they cross into
  Triton, and losing the flags at the boundary costs real code quality -- most
  visibly `arith.divf`, which without `arcp` lowers to the IEEE division fixup
  sequence rather than a bare reciprocal.

  Not yet proposed upstream. Keep until Triton forwards these flags itself.

patch-fma-lds-swizzle.patch
  Swizzles the pipelined LDS tile for FMA dot operands, which
  composePaddedLayout does not cover and upstream leaves unswizzled.
  SwizzledSharedEncodingAttr::get returns vec = 1, perPhase = 1, maxPhase = 1
  whenever the dot's parent layout is not MFMA/WMMA/Nvidia MMA, and
  composePaddedLayout only covers CDNA4 MFMA and gfx1250 WMMA, so an f32 dot on
  a target without a matrix core gets no swizzle at all.
  getSharedEncIfAllUsersAreDotEnc gains composeSwizzledLayoutForFMA, called for
  blocked-parent operands after composePaddedLayout declines and before the
  generic dot-operand constructor. The helper accounts for target bank count
  and rows narrower than a complete bank row. It is limited to f32 because
  other FMA element types use different packed LDS access patterns.

  Stacks on patch10694.patch and must be applied after it: the shared orders
  expected in test/TritonGPU/amd/amd-pipeline-fma-lds-swizzle.mlir are the
  operand-major ones that patch introduces.

  Not filed upstream yet; upstream Triton has the same performance gap.
